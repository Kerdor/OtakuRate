## 1. Что это за проект

OtakuRate — веб-приложение для личной субъективной оценки аниме и манги/манхвы.

Главная идея:
- пользователь оценивает произведения по нескольким субъективным критериям;
- из критериев получается итоговая оценка 1–10;
- anime и manga имеют разные наборы критериев;
- пользователь хранит собственную библиотеку;
- позже OtakuRate становится центром синхронизации с внешними сервисами.

## 2. Главный принцип

**OtakuRate — source of truth.**

Если пользователь поставил произведению оценку в OtakuRate, именно эта оценка считается основной.

Внешние сервисы:
- Shikimori
- Senkuro
- MangaLib
- ReManga
- другие будущие источники

являются внешними интеграциями.

## 3. Будущая синхронизация

Целевой сценарий:

Пользователь:
1. оценивает anime в OtakuRate;
2. OtakuRate знает соответствующие внешние ID;
3. подключённые интеграции получают новую оценку;
4. оценка записывается во внешние сервисы.

Для manga действует отдельная запись произведения и отдельная оценка.

Планируется browser extension, потому что некоторые сайты могут не предоставлять удобный OAuth/API для записи данных.

Предпочтительная модель безопасности:
- токены внешних сервисов хранятся локально в расширении;
- сервер OtakuRate не получает их без необходимости;
- расширение выполняет локальные действия с внешним сайтом;
- OtakuRate сообщает, что именно нужно синхронизировать.

## 10. Решённые решения по системе оценок

- Оценки пользователя хранятся отдельно от глобального `Title` в `UserRating`.
- Основная шкала — целые значения от 1 до 10; дробные оценки пользователю не выставляются.
- Значения отдельных критериев также целые 1–10 и сохраняются в `criteria_values`.
- Итог считается детерминированно как взвешенное среднее критериев и округляется до ближайшего целого.
- На этапе 3.1 значения критериев хранятся JSON-объектом внутри `UserRating`; вопрос о нормализации отдельными строками остаётся открытым.

## 14. Важные архитектурные намерения

### Версионирование системы рейтинга

Профиль критериев и его веса версионируются. `UserRating` хранит версию профиля, использованную при расчёте. Изменение весов создаёт новую версию и не должно задним числом менять старые оценки.

### LibraryEntry как центральная пользовательская связь

Основная связь пользователя с произведением: `User → LibraryEntry → Title`. Статус, прогресс, заметки и связь с пользовательской оценкой относятся к LibraryEntry/пользовательскому слою, а не к глобальному Title.

### Внешние источники

`ExternalSource` описывает сервис целиком, `ExternalTitle` связывает глобальный Title с конкретным ID источника, `UserExternalAccount` описывает подключение конкретного пользователя. Эти сущности не смешиваются.

### Сопоставление Title

Нельзя автоматически объединять произведения только по строковому названию. Внешний ID — основной надёжный идентификатор; сомнительные совпадения проходят через кандидатов/уверенность и при необходимости ручное подтверждение.

### Синхронизация

Для будущей синхронизации закладываются `SyncJob`, `SyncOperation`, `SyncResult`, `SyncConflict`. Операции независимы по источникам, должны поддерживать повтор и идемпотентность.

### Разделение Title и UserRating

Один Title может быть оценён многими пользователями.

Поэтому:
- данные произведения не принадлежат конкретному пользователю;
- оценки принадлежат пользователю;
- библиотека принадлежит пользователю;
- внешние ID принадлежат связи произведения с внешним источником.

### Разделение anime/manga

Не делать два полностью независимых приложения.

Общие:
- Title
- User
- LibraryEntry
- ExternalTitle
- Rating infrastructure

Различаться могут:
- наборы критериев;
- параметры прогресса;
- отдельные настройки.

### Интеграции

Не писать код Shikimori/Senkuro непосредственно внутри core/domain.

Внешний источник должен быть adapter/plugin-слоем.

### Масштабирование

Сначала простая реализация. Не добавлять Redis, Celery, отдельные сервисы, микросервисы и прочее до появления реальной необходимости. Синхронизацию сначала можно реализовать сервисно/через простые DB-backed jobs.

### Завершён 2.3 — внешние идентификаторы

Добавлены:
- `ExternalSource` — описание внешнего сервиса;
- `ExternalTitle` — связь глобального Title с внешним ID;
- `UserExternalAccount` — пользовательское подключение к источнику.

`ExternalTitle` поддерживает URL, тип медиа, название/альтернативные названия источника и дополнительный metadata. Один внешний ID уникален в пределах конкретного источника, поэтому один Title может иметь несколько источников. Отсутствие внешнего ID полностью допустимо.

`UserExternalAccount` не хранит токены/секреты и отделён от описания самого источника. Для одного пользователя предусмотрено не более одного подключения к одному источнику на текущем этапе.

Добавлена миграция `0004_external_sources` и тесты уникальности внешних ID и пользовательских подключений.

### Завершён 2.4 — связи произведений

Добавлены `TitleRelation` и `TitleRelationType` для связи произведений без объединения их в один `Title`. Поддержаны адаптации anime ↔ manga, сезоны, сиквелы, приквелы, спин-оффы, side story, альтернативные версии и связанные произведения.

`TitleRelation` хранит направленную связь между двумя `Title`, тип связи и необязательный `order_index`. Самосвязи запрещены, одинаковая связь одного типа не дублируется.

Для основы франшиз добавлены `Franchise` и `FranchiseTitle`. Один `Title` может быть связан с франшизой через отдельную таблицу, поэтому принадлежность к франшизе не влияет на идентичность самого произведения.

Добавлена миграция `0005_title_relations` и тесты моделей, сезонного порядка, запрета самосвязей/дубликатов и принадлежности к франшизе.

### Завершён 2.5 — сопоставление и дедупликация

Добавлен `TitleMatchCandidate` для неопределённых совпадений: внешний источник, внешний ID, кандидат `Title`, confidence, статус `pending/confirmed/rejected` и evidence.

`services/title_matching.py` использует пару `source_id + external_id` как основной надёжный сигнал. Совпадение только по названию не разрешает автоматическое объединение.

Повторный импорт того же внешнего ID не должен создавать новый `Title`: `ExternalTitle` уже имеет уникальное ограничение по `source_id + external_id`, а сервис позволяет найти существующий `Title` по этой паре.

Добавлены тесты для внешнего ID, запрета merge только по названию и хранения спорного кандидата с confidence.

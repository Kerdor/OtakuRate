# OtakuRate — Context

> Этот файл нужен для продолжения разработки в новом чате без восстановления всей истории.
> Его нужно обновлять после каждого значимого архитектурного решения и завершённого этапа.

## 1. Что это за проект

OtakuRate — веб-приложение для личной субъективной оценки аниме и манги/манхвы.

Главная идея:
- пользователь оценивает произведения по нескольким субъективным критериям;
- из критериев получается итоговая оценка 1–10;
- anime и manga имеют разные наборы критериев;
- пользователь хранит собственную библиотеку;
- позже OtakuRate становится центром синхронизации с внешними сервисами.

## 2. Главный принцип

**OtakuRate — source of truth.**

Если пользователь поставил произведению оценку в OtakuRate, именно эта оценка считается основной.

Внешние сервисы:
- Shikimori
- Senkuro
- MangaLib
- ReManga
- другие будущие источники

являются внешними интеграциями.

## 3. Будущая синхронизация

Целевой сценарий:

Пользователь:
1. оценивает anime в OtakuRate;
2. OtakuRate знает соответствующие внешние ID;
3. подключённые интеграции получают новую оценку;
4. оценка записывается во внешние сервисы.

Для manga действует отдельная запись произведения и отдельная оценка.

Планируется browser extension, потому что некоторые сайты могут не предоставлять удобный OAuth/API для записи данных.

Предпочтительная модель безопасности:
- токены внешних сервисов хранятся локально в расширении;
- сервер OtakuRate не получает их без необходимости;
- расширение выполняет локальные действия с внешним сайтом;
- OtakuRate сообщает, что именно нужно синхронизировать.

## 8. Решённые решения по системе оценок

- Оценки пользователя хранятся отдельно от глобального `Title` в `UserRating`.
- Основная шкала — целые значения от 1 до 10.
- Значения отдельных критериев также целые 1–10 и сохраняются в `criteria_values`.
- Итог считается детерминированно как взвешенное среднее критериев и округляется до ближайшего целого.
- На этапе 3.1 значения критериев хранятся JSON-объектом внутри `UserRating`.

## 9. Решённые архитектурные намерения

### Версионирование системы рейтинга

Профиль критериев и его веса версионируются. `UserRating` хранит версию профиля, использованную при расчёте. Изменение весов создаёт новую версию и не должно задним числом менять старые оценки.

### LibraryEntry как центральная пользовательская связь

Основная связь пользователя с произведением: `User → LibraryEntry → Title`. Статус, прогресс, заметки и связь с пользовательской оценкой относятся к пользовательскому слою, а не к глобальному Title.

### Внешние источники

`ExternalSource` описывает сервис целиком, `ExternalTitle` связывает глобальный Title с конкретным ID источника, `UserExternalAccount` описывает подключение конкретного пользователя. Эти сущности не смешиваются.

### Сопоставление Title

Нельзя автоматически объединять произведения только по строковому названию. Внешний ID — основной надёжный идентификатор; сомнительные совпадения проходят через кандидатов/уверенность и при необходимости ручное подтверждение.

### Интеграции

Внешний источник должен быть adapter/plugin-слоем. Код конкретного сайта не помещается в core/domain.

### Масштабирование

Сначала простая реализация. Не добавлять Redis, Celery, отдельные сервисы, микросервисы и прочее до появления реальной необходимости.

## 10. Прогресс

- `progress_current` / `progress_total` остаются универсальными полями.
- Для anime `progress_current` означает просмотренные серии.
- Для manga `progress_current` означает прочитанные главы.
- Общее известное количество должно учитывать максимум подтверждённого значения среди авторитетных источников.
- Обычный импорт/экспорт не должен молча переносить пользовательский прогресс.

## 6.3 — импорт из Shikimori

Реализован импорт пользовательского списка из Shikimori.

- ShikimoriAdapter.fetch_user_rates() получает anime/manga user rates через публичные user-rates endpoints.
- services/external_import.py сопоставляет записи по (source, external_id).
- Отсутствующие Title и ExternalTitle создаются автоматически.
- Статусы Shikimori маппятся в системные списки OtakuRate: watching/rewatching → watching, completed → completed, planned → planned, on_hold → paused, dropped → dropped; для manga watching/reading → reading.
- Прогресс (episodes, chapters, volumes) при импорте намеренно не записывается в LibraryEntry.
- Внешняя оценка хранится отдельно в UserExternalRating и не изменяет UserRating.
- Совпадения по названию не объединяются автоматически: создаются TitleMatchCandidate и возвращается ImportConflict для ручного решения.
- Добавлен POST /external/shikimori/import.
- Добавлена миграция 0016 для пользовательских внешних оценок после существующей цепочки 0013–0015.
- Добавлены unit/integration tests для импорта и адаптера.

## 13. Завершён 7.1 — capability-based Adapter API

Интеграционный слой переведён на общий capability-based контракт.

- `ExternalCapability` содержит стабильный набор операций: `search_titles`, `get_title`, `get_user_list`, `get_rating`, `set_rating`, `get_status`, `set_status`, `get_progress`, `set_progress`.
- `ExternalSourceAdapter` отвечает только за идентичность источника и список его capabilities.
- Операционные контракты разделены на отдельные Protocol: `TitleSearchAdapter` и `UserListAdapter`.
- Источник не обязан реализовывать неподдерживаемые операции.
- `services/external_search.py` проверяет capability поиска перед вызовом.
- `services/external_import.py` проверяет capability импорта пользовательского списка.
- `ShikimoriAdapter` сейчас объявляет только `SEARCH_TITLES` и `GET_USER_LIST`.
- Для совместимости сохранён `fetch_user_rates` как alias к `get_user_list`.
- Добавлены тесты capability-контракта и обновлены существующие тестовые адаптеры.

## 15. Завершён 7.3 — маппинг интеграций

- Добавлен `integrations/mapping.py` с общими функциями нормализации.
- Статусы сопоставляются с системными списками OtakuRate с учётом типа медиа.
- Прогресс нормализуется в универсальные `current/total`; это не означает автоматический импорт прогресса.
- Оценки переводятся в шкалу OtakuRate 1–10; пустое/нулевое значение трактуется как отсутствие оценки. Импорт продолжает хранить внешнюю оценку отдельно от `UserRating`.
- Типы медиа нормализуются из распространённых внешних названий; неизвестные типы вызывают понятную ошибку.
- Внешние ID нормализуются в непустые строки и остаются уникальными в рамках источника, а не глобально.
- Совпадение источника и внешнего ID — надёжное совпадение; совпадение названия — только кандидат на ручное подтверждение. Разные типы медиа не объединяются.
- Добавлены unit-тесты маппинга. Полный локальный набор тестов после этого блока должен запустить пользователь.

## 16. Завершён 8.1 — локальный аккаунт и авторизация

Реализован первый полноценный локальный auth-слой без привязки к внешним OAuth-провайдерам.

- В User добавлены password_hash и is_active; существующий dev-пользователь продолжает работать без пароля.
- Добавлена миграция 0017_local_auth.py.
- Регистрация: POST /auth/register.
- Авторизация: POST /auth/login.
- Выход: POST /auth/logout.
- Текущий пользователь: GET /auth/me.
- Сессии хранятся в подписанной cookie через SessionMiddleware; cookie HttpOnly и SameSite=Lax используются настройками Starlette, а в production включён Secure.
- В production OTAKURATE_SESSION_SECRET обязателен.
- Пароли хешируются scrypt через стандартную библиотеку Python, исходные пароли не сохраняются.
- User-scoped API и HTML-страницы получают пользователя из сессии. Передача чужого user_id отклоняется с 403.
- В dev-режиме отсутствие авторизованной сессии по-прежнему использует локального dev-пользователя, чтобы не ломать текущий MVP-сценарий.

Полный набор тестов после реализации 8.1 не запускался по текущему рабочему процессу; проверка будет выполнена позже общим прогоном.
